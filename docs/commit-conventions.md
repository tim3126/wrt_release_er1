# 提交规范

本文定义 `wrt_release` 的提交消息与提交边界。目标是让每个提交可独立审查、可回滚，并能从 Git 历史判断其原因、实际影响和已完成的验证。

它适用于所有设备；涉及 Taiyi/ER1 固件、构建身份、软件源、签名、镜像或发布工作流的改动，还必须遵守 [Taiyi 构建与发布流程](taiyi/build-release.md) 和 [Taiyi 验收矩阵](taiyi/validation.md)。

## 基本格式

标题采用 Conventional Commit 格式：

```text
<type>(<scope>): <简明动作>
```

- 标题使用小写英文 `type` 和 `scope`，冒号后使用简短、明确的中文动作描述。
- 标题描述已完成的改动，不使用“尝试”“临时”“可能”等不确定措辞。
- 一个提交只解决一个可审查的问题或交付一个完整的小功能；不要混入无关格式化、生成物、个人环境文件或另一设备的改动。
- 只有真实关联时才使用 `Fix: #<issue>` 或 `Refs: #<issue>` footer；不要为满足格式虚构 issue。

当前项目常用的类型为：

| 类型 | 使用场景 |
| --- | --- |
| `feat` | 新能力、设备支持或用户可用的功能 |
| `fix` | 已知错误、构建失败、兼容性或安全缺陷修复 |
| `refactor` | 不改变预期行为的结构调整 |
| `docs` | 文档、运维说明或决策记录 |
| `test` | 测试、不变量或验收脚本 |
| `build` | 本地构建编排、容器或构建工具 |
| `ci` | GitHub Actions、发布门禁或 CI 流程 |
| `config` | 可复用配置、fragments 或默认值 |
| `chore` | 不属于上述类别的维护性调整 |
| `revert` | 明确撤销指定提交或行为 |

优先使用已有、能说明影响面的 scope，例如 `taiyi`、`er1`、`build`、`release`、`feeds`、`packages`、`docker`、`netfilter`、`theme`、`delivery`、`fragments`。新增 scope 前先确认已有 scope 无法准确表达；不要使用个人姓名、临时目录名、日期或版本号作为 scope。

示例：

```text
feat(taiyi): 迁移至可复现的签名 APK 固件基线
fix(feeds): 修复受控软件源索引校验失败
refactor(config): 拆分设备通用配置片段
docs(build): 明确固定容器的构建身份
ci: 收紧发布产物白名单
revert(build): 恢复 Lucky 同步失败兼容行为
```

## 正文要求

标题不足以让审查者判断风险、验证和回滚边界时，必须写正文。复杂的固件、签名、依赖、发布、网络、安全和 CI 改动使用以下结构；与本次无关的段落可以省略，不能用空泛文字填充。

```text
<type>(<scope>): <简明动作>

根因：说明现有行为、触发条件和为什么需要修改。

实现：说明改变了哪些边界、输入或不变量；列出关键取舍。

安全与交付：说明信任边界、升级/回滚约束、禁止事项或发布门禁。

验证：列出实际执行的检查、范围和结果；未运行的检查明确写出原因。

Fix: #<issue>
```

- `根因` 只陈述已证实的事实，区分日志证据、复现结果和推断。
- `实现` 说明行为变化，不逐文件复述 diff；涉及固定输入时记录完整 commit、digest 或 SHA-256。
- `安全与交付` 用于密钥、签名、仓库、TLS、权限、刷写、发布和回滚边界。不得在提交消息中写入密码、私钥、token、完整代理节点或敏感备份路径。
- `验证` 必须是已经实际执行的命令或验收结果。不要把计划执行、静态阅读或未完成的实机测试写成通过。
- 固件候选与已部署/已发布是不同状态。构建和离线验收通过，不等于已刷写；实机通过，也不等于已创建 tag 或 Release。

`058958548314380ca82810e244cde866a0943387` 是 Taiyi 复杂基线迁移提交的正文范例：它依次记录了根因、实现、安全与交付和验证。后续提交应复用其信息密度与可验证性，而不是复制其中版本、哈希、数量或部署结论。

## 固件与发布专用记录

以下改动除了常规正文，还必须记录相应身份和结论：

| 改动范围 | 最低记录 |
| --- | --- |
| 上游、feeds、配置或源码锁 | 旧/新输入身份、影响的设备 profile、是否需要 clean build |
| 容器或构建状态 | base digest、builder image identity、是否允许缓存复用及其条件 |
| APK/软件源/签名 | 公钥身份、仓库范围、TLS/签名策略、private key absence 验证 |
| kernel、DTS、image 或 sysupgrade | board、kernel ABI、镜像类型、刷写限制和回滚前提 |
| 发布 workflow | 触发方式、权限、产物白名单、environment/reviewer 与失败关闭行为 |
| 实机验收 | 设备身份、只读/写入边界、已完成项、未完成 soak 或恢复演练 |

不要把固件、APK、构建缓存、解压 rootfs、私钥、配置备份、临时日志或 `.codebase-memory/` 作为普通源代码提交。需要交付产物时，遵循项目发布流程和对应的校验清单。

## 提交前检查

提交前按改动范围完成以下步骤：

1. 查看 `git status --short` 和 `git diff --check`，确认不会覆盖或带入其他人的改动。
2. 使用精确路径暂存；用 `git diff --cached --name-only` 与 `git diff --cached` 复核暂存范围和内容。
3. 运行与风险相称的检查，例如 shell 语法、构建不变量、单元测试、Actionlint、配置/JSON 校验或固件静态验收。
4. 扫描将要提交的文本是否意外包含凭据、私钥或敏感配置；不要读取或输出完整 `.env`、备份或私钥来完成该检查。
5. 将实际命令、结果、已知限制写入提交正文或相邻的版本化文档。
6. 提交后用 `git show --check --stat HEAD` 复核最终对象；只有在单独授权后才 push、tag、创建 Release 或部署。

## 禁止事项

- 不把不相关的格式化、生成文件或本地环境状态混进功能提交。
- 不将构建成功表述为实机、稳定性观察或生产发布已通过。
- 不以浮动分支、浮动容器 tag 或未验证的软件源身份描述可复现交付。
- 不在未经授权时创建 tag、push、Release、刷写固件、修改运行设备配置或重启设备。
- 不用 `sysupgrade -F`、猜测性分区写入或错误镜像类型掩盖兼容性失败。
